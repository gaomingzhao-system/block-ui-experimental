A FEW SIMPLE STEPS

Make yourself at home.

A component is one piece of HTML, with everything it needs inside.

From the collection to your page

  1. Choose a component and open its Get HTML panel.
  2. Focus the source field. Select all, then copy using your keyboard or your device’s selection menu. You can also download the HTML file.
  3. Paste the entire snippet into an HTML page or an editor that preserves raw HTML, <style> elements, and style attributes.
  4. Replace the demo text, destinations, and heading levels. Open your page and check its narrowest layout.

There is no installation step, build command, framework, CDN, or shared component stylesheet. Open index.html from this documentation folder to browse locally, or serve the folder with any static web server.

Copying, without a script

HTML and CSS cannot write text to the system clipboard on a button click. This library keeps the no-JavaScript promise: Get HTML opens a native disclosure, the readonly field lets you select source, and the download link saves the same snippet.

On Windows or Linux, use Ctrl + A, then Ctrl + C inside the field. On macOS, use ⌘ + A, then ⌘ + C. On touch devices, use Select All and Copy. Download behavior depends on the browser and works best when the documentation is served over HTTP or HTTPS.

What travels with a component

Every component has a semantic outer element, essential inline styles, and an embedded <style> element as its first child. All embedded rules live in @scope to ([data-bui]) { … }, so they target that component and stop at nested component roots.

Inline styles keep the basic presentation readable when scoped CSS is unsupported. Scoped rules add responsive refinements and focus or hover styles. Keep the style element inside its original wrapper, before the component content. The current HTML standard permits body style elements under these constraints.

Scope limits outgoing selectors. It is not a shadow boundary: your page’s CSS, inherited properties, or declarations using !important can still influence a component. Test the actual page where you embed it. A nested component can inherit custom properties from its ancestors; set its own values when you want a different theme.

Sanitized Markdown, email clients, and some blog editors remove styles or raw HTML. Those environments are outside the supported embedding contract. Test your editor’s published output. Do not disable its security filters just to use a snippet.

A Content Security Policy that blocks inline styles also blocks this distribution format. Integrate it with your site’s existing style policy; do not weaken a strict production policy automatically. Sites that cannot permit inline styles need a separate stylesheet integration, which is outside this library’s copy-and-paste format.

A small, useful palette

Set supported variables directly on the outer element, alongside its existing inline declarations. Each component uses fallbacks, so no token file is required. For example:

--bui-accent: #4338ca;
--bui-text: #20242e;
--bui-muted: #555d6d;
--bui-surface: #ffffff;
--bui-tint: #f6f4fc;
--bui-border: #e3e3ec;

Change foreground and background colors together and check contrast. Snippets use a light palette by default. The documentation’s Dark theme control changes the reading interface only; component previews keep their own colors. Theme selection applies to the current page and is not stored.

Change visible text in the markup, keep meaningful labels, and use links for navigation. Demo identities are fictional, and example.com destinations are placeholders to replace before publishing.

Modern features, useful fallbacks

Feature and fallback behavior
FeatureUseFallback
Inline styles, Grid, FlexboxBasic layout and appearanceThe content keeps semantic HTML structure.
Implicit @scopeLocal responsive and interactive stylesInline base styles remain; enhanced states may use native browser styling.
details / summaryAccordions, source panels, mobile navigationNative HTML behavior; no script is required.
:has()The documentation theme controlThe control is hidden and the default theme remains in browsers without support.

The design targets modern browsers. Browser support and the body-style rules continue to evolve; older HTML validators may not understand implicit scoped styles. Review actual diagnostics rather than disabling validation wholesale. See the HTML style element standard, CSS scope documentation, and the Clipboard API specification.

Built for readers

Native links and disclosures support keyboard use. Focus indicators remain visible, table headers describe their cells, and meaning does not rely on color alone. There is no required animation, autoplay, or custom keyboard model.

  • Preserve summary as the first child inside each details element.
  • Match heading levels to your article’s outline.
  • Keep table captions and scope attributes when editing tables.
  • Keep meaningful link text and visible labels.
  • Test your final content with keyboard navigation, large text, and a screen reader.

The initial fragments have no IDs and do not group disclosures by name, so you can paste the same fragment more than once. Give any IDs you add unique values.

Publish the documentation

The docs/ folder is a complete static site. Upload it as the publish directory on a static host. It uses relative links and includes its snippet downloads, license, and stylesheet, so it also works below a repository path.

For GitHub Pages, after merging the PR, select Deploy from a branch, choose main and /docs in repository Pages settings. No deployment has been enabled automatically. The empty .nojekyll file keeps the site as ordinary static files.

Review QUALITY.md in the repository for the checks performed and the remaining browser coverage. Production readiness is specific to your browser targets, editor, policy, and final content.
